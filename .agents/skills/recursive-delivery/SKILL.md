# Recursive Delivery

複数の成果物や依存関係を含む依頼を、受入れ可能な小さな作業単位へ分けて完了させる。
SA、PM、PG、Debugは別の人や別エージェントを意味しない。同じ担当者が役割を意識的に
切り替え、各単位で「定義 → 実装 → 検証 → 受入れ」を閉じるためのチェックポイントである。

## 使う条件

- 依頼が複数の独立した変更や依存関係を含む。
- 仕様・設計・実装・検証を順番に積み上げる必要がある。
- ユーザーが段階的な実行、役割交代、作業単位ごとの記録やコミットを求めている。

単一ファイルの単純な修正は、このループを無理に細分化せず、必要な確認だけを行う。

## 最初に確定すること

リポジトリの指示に従い、作業開始時に次を確認する。

- 適用される `AGENTS.md`、`README.md`、関連仕様、ADR、近傍の実装・テスト。
- 現在のブランチ、作業ツリー、既存の変更。無関係な変更や未追跡ファイルを保護する。
- 目的、対象範囲、非対象、受入れ条件、依存関係、プラットフォーム境界。
- 変更対象、参照専用ツリー、生成物、キャッシュ、外部サービスの境界。

仕様や契約を変更する場合は、リポジトリが定める仕様・ADR・変更手順を先に確認する。
存在しないマニフェスト、役割、スクリプト、コマンドを前提にして作業を止めない。

## 作業単位のループ

依存関係の順に、次のループを繰り返す。1単位は単一の主責務に限定し、定義・実装・検証・
受入れを一緒に説明できる大きさにする。曖昧な場合はさらに分割する。

### 1. SA — 境界と根拠を定める

- 現在の単位の名前と単一の目的を決める。
- 根拠となる仕様・ADR・既存実装を特定する。
- 対象、非対象、契約・データ形式・ユーザー動作への影響を明記する。
- 必要な証拠レベルと、単位を閉じるための最小検証を決める。

### 2. PM — 成果物と受入れを定義する

- 必要な要件、設計メモ、インターフェース、ToDoを更新する。
- 活動ではなく、確認可能な成果物として単位の完了条件を書く。
- 次に実行できる具体的な検証コマンドまたは確認方法を決める。
- 定義が広すぎる場合は実装前に分割する。

### 3. PG — 最小の変更を実装する

- 現在の単位に必要なファイルだけを変更する。
- 既存のアーキテクチャ、依存関係、命名、パッケージ管理を尊重する。
- 生成ファイル、ロックファイル、参照専用ツリーは指示がない限り直接変更しない。
- 動作変更には、可能な限り対象境界のテストまたは再現可能な検査を追加・更新する。

### 4. Debug — 定義に対して検証する

- 実装を直感ではなく、仕様・設計・受入れ条件と比較する。
- 失敗時は再現、原因分離、最小の恒久修正、再検証の順に進める。
- 静的検証、対象パッケージ検証、統合検証、実機検証を混同しない。
- 契約の不一致が見つかった場合は、実装を広げずSA/PMへ戻って仕様判断を行う。

### 5. PM受入れ — 単位を閉じる

- 受入れ条件を一つずつ確認し、完了・未完了・未検証を分ける。
- 変更範囲、根拠、実行コマンド、結果、未検証事項、次の安全な単位を記録する。
- このリポジトリで意味のある作業を完了した場合は、`TelopFlow_Feature/docs/work_history/`
  に指定形式の日本語作業履歴を追加する。
- 実機、別OS、Premiere Pro、外部サービスなど未実行の条件を成功扱いにしない。

### 6. コミットと次の単位

- ユーザーまたはリポジトリ指示がコミットを求める場合だけ、閉じた単位のファイルを選んで
  コミットする。無関係な変更を混ぜない。
- コミット前に `git status`、差分、ステージ内容を確認し、コミット後に状態を再確認する。
- 次の単位は依存関係順に選び、未検証の前提を隠したまま先へ進めない。

## 標準チェック

変更内容に応じて、リポジトリ標準のコマンドを優先する。Rustや共有基盤に影響する変更では、
通常は次を実行する。

```bash
mise run check
git diff --check
```

対象を限定できる場合は、先に最小の静的確認・型確認・テストを実行し、その後必要な範囲へ
広げる。失敗した場合は実際のエラーを分類し、コード・依存関係・環境・認証・ネットワークを
区別して記録する。

## 停止とエスカレーション

次の場合は、推測で範囲を広げず停止して方向を求める。

- 受入れ条件や公開契約を変更する承認が必要。
- 既存の無関係な変更と安全に分離できない。
- 人間の判断、ライセンス、秘密情報、実機、外部サービスの状態が必要。
- 次の単位の安全な前提や依存関係が確定できない。

停止時も、確認済みの事実、未解決の判断、必要な次の入力を具体的に報告する。
