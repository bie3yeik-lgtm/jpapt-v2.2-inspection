## 2. Canonical integration boundary

The production request/completion boundary is:

```text
largoyo/Premiere-AutoProcess-Plugin
  -> repository_dispatch: jpapt.candidate-request
  -> bie3yeik-lgtm/jpapt-v2.2-inspection
       Candidate Request Gateway
         -> Rust normalization / routing / execution identity
         -> execute=false: plan / resolve / estimate only
         -> execute=true: Candidate Package Evaluate V2
              -> completion or rejection evidence
              -> requested receipt_repository
                   -> portable receiver validation
                   -> CandidateCompletionAckV1
                   -> jpapt.candidate-completion-ack
                        -> Rust receipt/ACK binding validation
                        -> lifecycle persistence / reconciliation
                        -> acknowledged
```

Identity rules:

- `request_id` is the logical correlation identity across retry/reconciliation.
- `request_execution_id` identifies one concrete Gateway/V2 execution.
- caller-provided execution identity is not authoritative.
- direct V2 execution identity is `eval-<evaluation_run_id>-<evaluation_run_attempt>`.
- Gateway execution identity is generated by the Gateway authority.
- receipt, ACK, lifecycle state, evaluation run identity, repository binding, and canonical receipt SHA-256 must agree before a completion is acknowledged.

## 4. Credential and Environment model

### 4.1 `Private-Secrets`

The public repository uses GitHub Environment:

`Private-Secrets`

Environment-scoped credentials are injected only into jobs that explicitly declare that Environment. A job that references an Environment Secret without `environment: Private-Secrets` must be treated as unbound and will not receive that credential.

Environment attachment is a capability boundary. It must be added only to jobs that need the protected credential.

### 4.2 Token role separation

The current least-privilege split is:

| Credential | Authority / intended use |
| --- | --- |
| `SOURCE_REPO_TOKEN` | read the real private source repository and its routing/config data |
| `TARGET_REPO_TOKEN` | inspect/deliver to external receiver repositories and the dedicated fixture |
| `JPAPT_ACK_TOKEN` | ACK return capability; fixture/private receiver secret is scoped to dispatch back to the orchestrator |
| `HF_TOKEN` | Hugging Face model/Bucket access required by the selected public route |

`SOURCE_REPO_TOKEN` must not be broadened merely to manage the E2E receiver fixture. Receiver operations belong to `TARGET_REPO_TOKEN`.

`Candidate Package Evaluate V2` therefore keeps source routing on `SOURCE_REPO_TOKEN`, while external completion delivery uses `TARGET_REPO_TOKEN`. `Candidate Protocol Readiness` and `Candidate Protocol E2E` use the receiver capability rather than the source capability when verifying the external receiver.

### 4.3 Current TARGET token capability boundary

The dedicated fixture is selected by `TARGET_REPO_TOKEN`, but the current fine-grained PAT permissions are incomplete:

- fixture repository metadata: HTTP `200`
- normal Contents API for `.jpapt/candidate-receiver.json`: HTTP `403`
- raw Contents API for the same path: HTTP `403`

This proves that repository selection is correct and isolates the missing capability to repository Contents access.

The minimum additional capability required for canonical Readiness is:

`Contents: Read-only`

for `bie3yeik-lgtm/jpapt-protocol-e2e-source`.

Do not weaken Readiness to skip remote receiver manifest/hash verification. If later receiver bootstrap mutation is deliberately delegated to this PAT, stronger Contents write permission may be required, but that is separate from the minimum Readiness requirement.

### 4.4 Token handling rules

- never put token values in dispatch payloads, artifacts, summaries, schemas, documentation, or logs;
- do not enable shell tracing around credential-bearing commands;
- distinguish token existence, Environment injection, repository selection, and endpoint permission;
- HTTP acceptance of a dispatch is not protocol completion;
- fail closed on wrong orchestrator, wrong receiver, wrong execution identity, wrong receipt SHA, or malformed evidence.

## 6. Candidate Request Gateway contract

Common ingress is:

```text
repository_dispatch event_type = jpapt.candidate-request
```

The Gateway validates/resolves at least:

- request identity;
- source repository;
- receipt repository;
- HF Bucket;
- candidate selection;
- package identity when applicable;
- dataset routing;
- suite (`smoke`, `parity`, `probe`);
- executor (`github`, `hf_jobs`);
- execution environment;
- HF Jobs flavor/image when applicable;
- `dry_run` / `execute` intent.

`execute=false` is the safe planning boundary and must not start model evaluation, HF Jobs, destructive Bucket mutation, or unreviewed external execution.

The source repository routing config is fetched and validated; missing source configuration must not be silently guessed into a production route.

## 7. Completion, rejection, and ACK contract

Completion evidence is bound to:

- `request_id`;
- `request_execution_id`;
- source repository;
- receipt repository;
- orchestrator repository;
- evaluation run ID/attempt;
- canonical receipt SHA-256;
- conclusion;
- dry-run/compute semantics.

The portable receiver validates the portable protocol boundary and builds an ACK. After the ACK returns, the public Rust authority validates receipt, ACK, and binding before durable acknowledged state is accepted.

Duplicate valid completion must be idempotent. Malformed, cross-execution, wrong-repository, wrong-orchestrator, or wrong-receipt-SHA evidence must fail closed even when `request_id` matches.

## 8. HF Jobs boundary

HF Jobs is an execution backend, not protocol authority.

When the HF Jobs route is selected, authority requires:

- supported suite semantics;
- digest-pinned image identity;
- image reachability/preflight before paid remote execution;
- canonical plan/result/receipt binding;
- strict provider evidence;
- result/evidence validation before successful completion rebinding.

Linux container success must not be treated as CoreML or DirectML proof, and CPU fallback must not be treated as proof of the requested accelerator/provider.
