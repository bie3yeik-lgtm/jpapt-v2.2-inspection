## 2. Canonical integration boundary

```text
largoyo/Premiere-AutoProcess-Plugin
  -> repository_dispatch: jpapt.candidate-request
  -> bie3yeik-lgtm/jpapt-v2.2-inspection
       Candidate Request Gateway
         -> Rust normalization / routing / execution identity
         -> execute=false: plan / resolve / estimate only
         -> execute=true: Candidate Package Evaluate V2
              -> completion or rejection authority object
              -> repository_dispatch transport envelope when required
              -> requested receipt_repository
                   -> portable receiver validation
                   -> CandidateCompletionAckV1
                   -> repository_dispatch ACK transport envelope when required
                   -> public ACK receiver
                        -> Rust receipt/ACK binding validation
                        -> lifecycle persistence / reconciliation
                        -> acknowledged
```

Identity rules:

- `request_id` is the logical correlation identity across retry/reconciliation.
- `request_execution_id` identifies one concrete Gateway/V2 execution.
- caller-provided execution identity is not authoritative.
- direct V2 execution identity is `eval-<evaluation_run_id>-<evaluation_run_attempt>`.
- Gateway execution identity is generated by the Gateway authority.
- receipt, ACK, lifecycle state, evaluation run identity, repository binding, and canonical receipt SHA-256 must agree before completion is acknowledged.

## 4. Credential and Environment model

### 4.1 `Private-Secrets`

The public repository uses GitHub Environment `Private-Secrets`.

Environment-scoped credentials are injected only into jobs that explicitly declare that Environment. A job that references an Environment Secret without `environment: Private-Secrets` is unbound and must not be assumed to receive the credential.

Environment attachment is a capability boundary and belongs only on jobs that need the protected credential.

### 4.2 Token role separation

| Credential | Authority / intended use |
| --- | --- |
| `SOURCE_REPO_TOKEN` | read the real private source repository and its routing/config data |
| `TARGET_REPO_TOKEN` | inspect, synchronize, and deliver to external receiver/fixture repositories; fixture acceptance currently also uses it as the ACK return credential because it has the required endpoint capability |
| `JPAPT_ACK_TOKEN` | receiver-side secret containing an ACK return credential capable of `repository_dispatch` to the orchestrator |
| `HF_TOKEN` | Hugging Face model/Bucket access required by the selected public route |

`SOURCE_REPO_TOKEN` must not be broadened merely to manage the E2E receiver fixture. Receiver operations belong to `TARGET_REPO_TOKEN`.

`Candidate Package Evaluate V2` keeps source routing on `SOURCE_REPO_TOKEN`; external completion delivery uses `TARGET_REPO_TOKEN`. `Candidate Protocol Readiness` and `Candidate Protocol E2E` likewise use the receiver capability when verifying the external receiver.

The fixture ACK credential must be endpoint-capable, not merely a valid PAT. Live evidence showed the distinction:

- an older fixture `JPAPT_ACK_TOKEN` value failed with HTTP `401 Bad credentials`;
- replacing it with the current `SOURCE_REPO_TOKEN` produced HTTP `403 Resource not accessible by personal access token` on `repository_dispatch` despite repository metadata showing write access;
- replacing it with the current `TARGET_REPO_TOKEN` allowed the fixture receiver ACK-dispatch step to complete successfully.

This is why token validity, repository selection, collaborator-level write state, and fine-grained endpoint permission must be treated as separate checks.

### 4.3 Current TARGET capability

The previous fixture Contents blocker is resolved. `TARGET_REPO_TOKEN` now supports the live operations required by the acceptance harness, including:

- fixture repository access;
- managed Contents read/write used for controlled fixture synchronization;
- live receiver manifest/hash verification;
- completion delivery to the fixture;
- ACK return dispatch to the public orchestrator in the dedicated acceptance fixture.

R/W is acceptable for this fixture-management capability. A separate readiness-only credential could be narrower, but the current token also performs managed synchronization and therefore need not be Read-only.

### 4.4 Token handling rules

- never put token values in dispatch payloads, artifacts, summaries, schemas, documentation, or logs;
- do not enable shell tracing around credential-bearing commands;
- distinguish token existence, Environment injection, repository selection, and endpoint permission;
- HTTP acceptance of a dispatch is not protocol completion;
- fail closed on wrong orchestrator, wrong receiver, wrong execution identity, wrong receipt SHA, or malformed evidence.

## 6. Candidate Request Gateway contract

Common ingress is `repository_dispatch` event type `jpapt.candidate-request`.

The Gateway validates/resolves at least request identity, source and receipt repositories, HF Bucket, candidate/package identity, dataset routing, suite (`smoke`, `parity`, `probe`), executor (`github`, `hf_jobs`), execution environment, HF Jobs flavor/image when applicable, and `dry_run` / `execute` intent.

`execute=false` is the safe planning boundary and must not start model evaluation, HF Jobs, destructive Bucket mutation, or unreviewed external execution.

Source routing config is fetched and validated; missing source configuration must not be silently guessed into a production route.

## 7. Completion, rejection, ACK, and repository_dispatch transport

Completion evidence is bound to `request_id`, `request_execution_id`, source repository, receipt repository, orchestrator repository, evaluation run ID/attempt, canonical receipt SHA-256, conclusion, and dry-run/compute semantics.

The portable receiver validates the protocol authority object and builds an ACK. After the ACK returns, the public Rust authority validates receipt, ACK, and binding before durable acknowledged state is accepted.

### 7.1 Authority object versus transport envelope

GitHub `repository_dispatch` limits `client_payload` to at most 10 top-level properties. `CandidateCompletionReceiptV1`, `CandidateCompletionAckV1`, and `CandidateRequestRejectionV1` may legitimately exceed that limit.

The authority objects therefore remain unchanged, while transport adapts oversized payloads as:

```json
{
  "event_type": "jpapt.candidate-completed",
  "client_payload": {
    "protocol_payload": {
      "...": "unchanged authority object"
    }
  }
}
```

The same envelope rule applies to ACK/rejection when required. Receiver workflows accept both the canonical nested transport and the legacy flat transport for backward compatibility. Canonical receipt SHA-256 is calculated over the authority object, never the GitHub transport envelope.

Live evidence that motivated this rule: evaluation run `32265420082` produced a valid completion receipt but GitHub rejected the old flat transport with HTTP `422` because 25 `client_payload` properties were supplied.

### 7.2 Idempotence and negative routing

Duplicate valid completion must be idempotent. Malformed, cross-execution, wrong-repository, wrong-orchestrator, or wrong-receipt-SHA evidence must fail closed even when `request_id` matches.

## 8. HF Jobs boundary

HF Jobs is an execution backend, not protocol authority.

When selected, authority requires supported suite semantics, digest-pinned image identity, image reachability/preflight before paid remote execution, canonical plan/result/receipt binding, strict provider evidence, and result/evidence validation before successful completion rebinding.

Linux container success is not CoreML or DirectML proof, and CPU fallback is not proof of a requested accelerator/provider.
