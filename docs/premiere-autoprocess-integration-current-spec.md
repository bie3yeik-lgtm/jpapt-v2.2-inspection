## 2. Authority precedence

For behavior owned by `jpapt-v2.2-inspection`, use this precedence order:

1. Rust interface and Rust runtime semantics
2. source-controlled protocol contracts
3. JSON Schema
4. source-controlled catalog/config
5. production workflow YAML
6. documentation
7. downstream/private integration notes

A lower-precedence layer must not redefine behavior established by a higher-precedence layer.

The private repository may implement local typed mirrors, fixtures, adapters, or policy gates, but those are compatibility/consumer layers and do not become public authority.

## 3. Current system boundary

The current canonical request/completion boundary is:

```text
largoyo/Premiere-AutoProcess-Plugin
  -> repository_dispatch: jpapt.candidate-request
  -> bie3yeik-lgtm/jpapt-v2.2-inspection
       Candidate Request Gateway
         -> Rust request normalization / routing / execution identity
         -> execute=false: plan / resolve / estimate only
         -> execute=true: Candidate Package Evaluate V2
              -> completion or rejection evidence
              -> repository_dispatch to requested receipt repository
                   -> portable receiver validation
                   -> CandidateCompletionAckV1
                   -> repository_dispatch ACK to orchestrator
                        -> Rust binding validation
                        -> lifecycle persistence / reconciliation
                        -> acknowledged
```

The logical correlation identity and execution identity are distinct:

- `request_id` identifies one logical caller request across retry/reconciliation;
- `request_execution_id` identifies one concrete Gateway/V2 execution;
- caller-provided execution identity is not authoritative;
- direct V2 E2E execution identity is `eval-<evaluation_run_id>-<evaluation_run_attempt>`;
- Gateway execution identity is generated by the Gateway authority.

Receipt, ACK, lifecycle state, evaluation run identity, repository binding, and canonical receipt SHA-256 must agree before a completion may be treated as acknowledged.

## 5. Secrets, Environments, and trust policy

### 5.1 Public orchestrator Environment

The public repository uses the GitHub Environment:

`Private-Secrets`

The following names are already provisioned there according to the current integration setup:

- `SOURCE_REPO_TOKEN`
- `JPAPT_ACK_TOKEN`
- `TARGET_REPO_TOKEN`

`TARGET_REPO_TOKEN` is not currently part of the required canonical public runtime path and must not be introduced into production behavior without a reviewed use case.

**Important:** Environment Secrets are injected only into jobs that explicitly reference the matching Environment. A workflow that merely uses `${{ secrets.SOURCE_REPO_TOKEN }}` or `${{ secrets.JPAPT_ACK_TOKEN }}` without `environment: Private-Secrets` will observe an empty value for those Environment-scoped secrets.

Therefore the previous provisioning failure recorded on Issue #70 as `source-repo-token-missing` does **not** prove the secret is absent. It proves that the job used for that test was not attached to the Environment that owns the secret.

Jobs requiring those Environment-scoped capabilities must use:

```yaml
jobs:
  <job>:
    environment: Private-Secrets
```

Environment attachment is a capability boundary, not merely a secret lookup convenience. Add it only to jobs that actually require the protected credential.

### 5.2 `HF_TOKEN`

`HF_TOKEN` is currently treated separately from the `Private-Secrets` Environment-scoped GitHub tokens.

Operational evidence from the private lifecycle Bucket smoke already proved that the configured workflow path can obtain `HF_TOKEN`, create/reuse a private Bucket, persist lifecycle evidence, read it back, and validate it without model/GPU/HF Jobs compute.

Do not move or duplicate `HF_TOKEN` solely for symmetry with GitHub tokens unless a separate credential-policy decision requires it.

### 5.3 Consumer/private repository ACK capability

`largoyo/Premiere-AutoProcess-Plugin` already provides `JPAPT_ACK_TOKEN` for the private receiver path.

When that repository is the requested `receipt_repository`, its portable receiver may use that capability to return `jpapt.candidate-completion-ack` to `bie3yeik-lgtm/jpapt-v2.2-inspection`.

The private receiver trust policy must explicitly allow only the intended orchestrator identity. The public orchestrator and any dedicated E2E fixture must fail closed on wrong orchestrator or wrong receipt repository bindings.

### 5.4 Token handling rules

- never place token values in dispatch payloads, artifacts, summaries, schemas, docs, or logs;
- do not enable shell tracing around credential-bearing commands;
- scope fine-grained PATs or GitHub Apps to the smallest repositories and operations practical;
- distinguish token existence from token reachability/permission;
- HTTP acceptance of a dispatch is not proof of protocol completion.

## 7. Candidate Request Gateway current contract

The common ingress is:

```text
repository_dispatch event_type = jpapt.candidate-request
```

The Gateway resolves and validates at least:

- `request_id`;
- source repository;
- receipt repository;
- HF Bucket;
- candidate selection;
- package identity where relevant;
- dataset source/id;
- suite (`smoke`, `parity`, `probe`);
- executor (`github`, `hf_jobs`);
- execution environment;
- HF Jobs flavor/image inputs where relevant;
- `dry_run` / `execute` intent.

`execute=false` remains the safe planning boundary. It must not launch model evaluation, HF Jobs, destructive Bucket mutation, or unreviewed downstream execution.

The source repository routing config is fetched from the source repository and validated; missing configuration must not be silently guessed into a production route.

## 8. Completion/rejection/ACK current contract

The canonical completion path is bound by:

- logical request ID;
- execution ID;
- orchestrator repository;
- source repository;
- receipt repository;
- evaluation run ID/attempt;
- canonical receipt SHA-256;
- conclusion;
- dry-run/compute semantics.

Portable receiver code exists because an arbitrary receiver repository is not required to carry the public Rust workspace. The receiver validates the portable schema/binding surface and constructs an ACK; once evidence returns to the orchestrator, Rust authority performs canonical receipt/ACK/binding validation before durable state is accepted.

Duplicate valid completion delivery must be idempotent. Malformed, cross-execution, wrong-repository, wrong-orchestrator, or wrong-receipt-SHA evidence must fail closed and must not be merged merely because `request_id` matches.

## 9. HF Jobs current boundary

HF Jobs support is not a replacement for the public contract or for GitHub-hosted orchestration.

Current authority requires, where the HF Jobs route is used:

- supported suite semantics as defined by the current Rust/workflow contract;
- a digest-pinned image identity;
- image reachability/preflight before paid remote execution;
- canonical plan/result/receipt binding;
- strict provider evidence rather than treating CPU fallback as proof of a requested accelerator/provider;
- result/evidence validation before successful completion receipt rebinding.

Do not treat Linux container success as CoreML or DirectML proof. Provider evidence levels such as compile/register/session/execution/assignment must not be collapsed into one generic success flag.
